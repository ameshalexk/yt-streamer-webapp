# Storage controls integration

`src/lib/storage-manager.js` exports the server integration surface:

- `summary()` returns `libraryBytes`, `cacheBytes`, `freeBytes`, `totalBytes`, `policy`, and processed `downloads` (`id`, `title`, `pinned`, `watchedAt`, `bytes`). Library usage includes files under `LIBRARY_DIR` plus processed-library downloads. Cache usage includes recommendation prepared and temporary files plus processed DASH cache and temporary files. Capacity values describe the filesystem containing `LIBRARY_DIR`; they are `null` when the platform cannot report them.
- `setPolicy({ enabled?, watchedRetentionDays? })` accepts only those keys, a boolean enable flag, and an integer retention between 1 and 3650 days. Initial policy is disabled with a 30-day retention.
- `setPinned(id, boolean)` protects a processed-library item from automatic watched cleanup.
- `markWatched(id)` records a completion timestamp. The server should call this only after validating a completion signal from the client; merely opening or stopping playback is not completion.
- `cleanup({ apply, ids? }, { busy? })` previews eligible downloads by default in `eligible`. Each item includes processed media `bytes` and removable DASH `cacheBytes`. An apply call requires an explicit list of up to 1000 IDs, enabled policy, and an idle server. IDs are deduplicated, downloads are re-listed, and metadata and paths are checked immediately before removal. Apply returns removed items plus `reclaimedBytes` and `reclaimedCacheBytes`.

Policy and per-download markers live in `DATA_DIR/storage-policy.json`; writes are serialized and atomic. Cleanup only calls the existing processed-library and processed-DASH removal functions. It never removes the regular `LIBRARY_DIR`, APNE/iCloud originals, playlist store, or recommendation cache. An APNE video registered inside the processed library can be eligible only after the server records its watched completion; its source and iCloud copy are outside cleanup scope.

Suggested route wiring is `GET /api/storage` → map summary fields to `{ usage: { libraryBytes, cacheBytes, freeBytes, totalBytes }, policy, downloads }`, `PATCH /api/storage/policy` → `setPolicy(req.body)`, `PATCH /api/storage/downloads/:id` → validate `{ pinned: boolean }` then `setPinned`, `POST /api/storage/downloads/:id/watched` → validate the server-authorized completion payload then `markWatched`, and `POST /api/storage/cleanup` → `cleanup(req.body, { busy })`, mapping `eligible` to `candidates` and computing reclaimable bytes from both `bytes` and `cacheBytes`. The root server must hold its maintenance barrier across apply and reject new media/API mutations for that interval; a one-time `busy` snapshot alone cannot prevent a job from starting after the check. The UI should send only IDs selected from a prior preview.
