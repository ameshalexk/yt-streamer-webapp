# TeslaMon Codex runtime feasibility — 2026-10-22

## Finding

The installed Codex App Server can provide a persistent Codex thread and client-implemented dynamic function tools. The installed CLI is `codex-cli 0.163.0-alpha.10.2`. Its version-matched experimental JSON Schema confirms `thread/start.dynamicTools`, function-only dynamic tool definitions, and the server-to-client `item/tool/call` request with `threadId`, `turnId`, `callId`, tool name, namespace, and model arguments. This is a viable mechanism for routing TeslaMon calls into the server's six bounded handlers while retaining thread history.

**It does not establish the required exclusive six-tool policy.** Neither the official App Server protocol nor the installed `thread/start` schema exposes an `allowedTools`/`disabledTools` control. The supported sandbox modes (`read-only`, `workspace-write`, `danger-full-access`) govern filesystem/process permissions; read-only still exposes read capability and is not tool removal. The official docs describe `dynamicTools` as additional client-executed tools and do not state that defining them replaces Codex's built-ins. The schema's `disabledPluginIds` applies to `turn/start`, and its description explicitly says it “Does not yet filter plugin capabilities.” Therefore, do not treat dynamic tools plus a restrictive prompt or read-only sandbox as proof that built-in shell, filesystem, web, or plugin tools are unavailable.

The App Server request has an arbitrary `config` object, but the version-specific schema and official App Server docs inspected here do not define a supported per-thread tool allowlist inside it. Guessing config keys, or changing the user's global config, would not establish a supported restriction. No model request was made to probe behavior. **Current concrete blocker:** the requested persistent Codex CLI/App Server runtime cannot yet be claimed to have actual six-tool-only confinement. Keep model execution disabled until a supported and verifiable exclusion mechanism is identified, or use an explicitly different runtime whose tool allowlist is enforced by construction.

## Exact evidence collected

- Official [Codex App Server documentation](https://developers.openai.com/codex/app-server) says App Server is the interface for rich clients and documents the initialize → thread start/resume → turn start/steer → streamed events lifecycle. It documents persistent thread history and `turn/interrupt` completion.
- The same page states `dynamicTools` on `thread/start` and `item/tool/call` are **experimental**. A call emits a dynamic-tool item and a server request to the client, which returns content. It cautions against reserved built-in namespace names. This supplies the custom-tool callback but does not claim the callback is the only available capability.
- The official `thread/start` example supports `approvalPolicy: "never"` and a sandbox choice, while its sandbox documentation defines read-only as filesystem access policy. These controls do not demonstrate tool inventory restriction.
- The generated schema from the installed CLI (`codex app-server generate-json-schema --experimental --out /tmp/teslamon-appserver-schema`) identifies `ThreadStartParams.dynamicTools` as nullable and defines each dynamic tool as a function (`name`, `description`, `inputSchema`, optional `deferLoading`) or namespace. `ThreadStartParams` has no `disabledTools` or `allowedTools` property. `TurnStartParams` likewise has no tool allowlist. `TurnInterruptParams` requires `threadId` and `turnId`.
- That schema describes `disabledPluginIds` as “Saved list of disabled plugin IDs. Does not yet filter plugin capabilities.” This is insufficient evidence for restricting capabilities.
- Installed CLI help confirms `app-server`, stdio as default transport, and schema generation. No model/auth request, persistent process, global config read/write, or credential access was performed. Schema artifacts are in `/tmp/teslamon-appserver-schema` only.

## Version-specific viable protocol, if/when confinement is proven

1. Start the locally installed App Server over stdio and do one `initialize` handshake with `capabilities.experimentalApi: true`; then send `initialized`.
2. `thread/start` a non-ephemeral thread with an explicit local `cwd`, chosen model, `approvalPolicy: "never"`, constrained sandbox and exactly six `dynamicTools` declarations (use non-reserved namespace, e.g. `teslamon`). Persist the returned `thread.id` and resume it for later turns. App Server docs say dynamic tools are persisted with the rollout and restored on resume if none are supplied.
3. `turn/start` each user utterance on that thread. Stream `item/agentMessage/delta`, item events and `turn/completed`; interrupt with `turn/interrupt` using the active `threadId` and `turnId` when the owning request is cancelled.
4. On each `item/tool/call`, dispatch by an exact six-name allowlist to the existing authenticated TeslaMon service. Validate arguments against server-side schemas and current owner/selected-device binding, enforce deadline/idempotency policy, return bounded content, and reject every unknown tool name. Never pass user-supplied identity or target authority from model arguments.
5. This protocol is only an integration route; runtime security acceptance still requires verified exclusion (or non-exposure) of every non-TeslaMon capability before any model request is enabled.

Official documentation currently recommends Codex SDK for automation/CI, while this product requires durable Codex conversation/thread semantics; the App Server is the matching persistent-thread interface but experimental dynamic tools alone leave the exclusion issue unresolved. An Agents API agent can enforce configured tool selection and an environment of `none`, but this changes the requested Codex CLI/App Server runtime and requires separate account/credential and product approval; it is an alternative research direction, not a drop-in proof for this task.

## Scope and next step

This research only created this note. It did not modify application code/configuration, start an App Server or model request, access secrets, or run device tests. Next, locate an official/currently supported App Server configuration mechanism that explicitly disables all built-in and plugin tools while retaining only supplied dynamic tools, then verify that tool inventory without submitting user content. If no such mechanism exists, the six-tool-only requirement is a platform blocker for Codex App Server and should be implemented with a different model runtime designed around a closed tool allowlist.

## Source implementation status — 2026-10-22

Added source-only protocol client `webapp/src/lib/teslamon-codex-runtime.js` and isolated wire-fixture tests `webapp/test/teslamon-codex-runtime.test.mjs`.

- Product APIs `getTeslaMonCodexRuntimeAvailability()`, `startTeslaMonCodexRuntime()` and `submitTeslaMonCodexRuntime()` always return `runtime_confinement_unverified`. There is no boolean or caller-supplied attestation override.
- The separately named low-level `createTeslaMonCodexProtocolDriver()` accepts an injected transport and server-owned playback dispatcher. It does not spawn a process, obtain credentials, or initialize a real model request itself. It supports initialize/initialized, six declared dynamic tools, persistent `thread/start` plus injected-store `thread/resume`, one active turn per context, and strict owner/controller/target-generation isolation.
- It validates all model-originated tool names, namespace, arguments, call IDs, active turn/thread binding, and a six-call per-turn cap. Every other server-initiated request gets a method-not-allowed JSON-RPC error. It contains no shell, filesystem, generic execution, web, plugin, or arbitrary-tool dispatcher. It only treats JSON-RPC frames with `result`/`error` and no `method` as responses to pending client requests; server requests cannot consume a matching numeric ID. Turn notifications are correlated by `threadId` plus the active turn ID, with `turn/start` response establishing that active ID; early tool calls wait until that response arrives.
- Timeout, caller cancellation, target-generation changes, and transport failure abort an in-flight private dispatch, make a best-effort `turn/interrupt`, drop the context's resumable reference when outcome is uncertain, and do not automatically replay. Normal shutdown preserves an idle thread ID through an injected synchronous `get/set/delete` thread store; thread IDs must be scoped by the server to the owner/controller/generation tuple. The model never sees those identifiers.
- `node --check src/lib/teslamon-codex-runtime.js` passed. `node --test test/teslamon-codex-runtime.test.mjs` passed **20/20** isolated fake-transport tests: fail-closed activation, handshake, six-tool declaration, tool allowlist/argument checks, call cap, unsupported server request rejection, context isolation, persistent resume, concurrent start coalescing/submission exclusion, timeout/cancel interruption, no replay, transport crash, colliding JSON-RPC IDs, stale completion correlation, pre-abort, abort during start, late old-generation creation, close during creation, invalidation during start, and concurrent initialize handshakes.
- This is not App Server/model acceptance: no real process, model call, sign-in, API key, plugin inventory, or device interaction was used. The public activation gate remains disabled because these fixtures cannot prove the installed App Server excludes built-ins. The caller integrating the low-level driver must still preserve that gate and supply only the authenticated six-action playback dispatcher. Context cancellation and generation invalidation are checked before and after thread acquisition; invalidated pending starts cannot store or publish their late thread ID. A pending `turn/start` cancelled by abort/invalidation waits for the response and interrupts its exact returned turn ID. Thread-store methods are synchronous so invalidation cannot interleave between final validation and thread-ID persistence.
