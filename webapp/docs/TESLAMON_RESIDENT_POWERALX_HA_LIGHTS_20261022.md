# TeslaMon resident PowerALX transcription and Codex-controlled HA lighting

Date: 2026-10-22. Scope: Mac-hosted `stream.ameshalex.com`; the HA-hosted webapp keeps its unsupported Codex capability gating. No changes to other YT Streamer playback engines.

## 1. Resident PowerALX GPU speech worker

- Windows startup script `scripts/teslamon-poweralx-run.cmd` starts `scripts/teslamon-poweralx-resident.py` using the **existing** Life Recorder release `phase1-20260912-b`, existing local model cache, `faster_whisper` Large-v3 CUDA FP16, Hindi/Malayalam ONNX and IndicTrans2 translator. Downloads and remote Hugging Face access disabled. This is not a new model or Mac-side ASR.
- User-scoped Windows Scheduled Task `TeslaMon Resident Speech`: trigger `ONLOGON`, execution limit `PT0S` (unlimited), restart up to three times with 1-minute interval on failure. Runs only when Windows user session is active; this is not a boot-time SYSTEM service. Worker code deployed under `C:\Users\Amesh\life-recorder-worker\teslamon-resident` and remains separate from the original Life Recorder source/release.
- Resident serves **only** `127.0.0.1:38491` on PowerALX. Nonce-like bearer token is stored only in a Windows-local file, not in Mac, GitHub, Cloudflare, or a browser. Every process request must contain a UUID and an already-uploaded, size/duration/SHA-validated job under the existing `teslamon-jobs` root. Caller is the authenticated Mac SSH process, which reads the token locally on PowerALX before invoking the loopback endpoint. Never expose the port to LAN/Internet.
- SSH/SCP Mac forwarding, Safari WebM->M4A normalization and SHA validation remain. New transcriber mode is enabled by `TESLAMON_POWERALX_RESIDENT=1` in Mac's **private** LaunchAgent. Default OFF for safe backward compatibility. Existing one-shot worker invocation remains the old behavior if not enabled; when enabled, it calls only the resident service (does not silently cold-start on failure).
- Shared GPU file lock is acquired during model loading and each processing call, then released. Model remains loaded in GPU memory while idle; other Life Recorder jobs retain the same GPU lock. If available GPU memory is insufficient for simultaneous large workloads, the user may stop the resident task.
- Observed NVIDIA RTX 5070 Ti memory before startup ~5.3 GiB allocated to existing applications; after resident ready ~9.2 GiB allocated: **~4.0 GiB additional VRAM**. Windows PowerShell private/committed memory for worker process ~5,922 MiB; its current physical working set ~140 MiB, not equivalent to all private commit. System physical RAM free ~11.9 GiB before and ~11.5 GiB after (variable). Raw Task startup took 34.13s, then remained running. Synthetic 2.5s WebM tone end-to-end through resident Mac->PowerALX->Mac returned expected `no_speech_detected` in 3.4s vs previous 10.3s with cold one-shot worker. Not a real speech accuracy/latency acceptance test.

## 2. Home Assistant light controls (Codex CLI actual MCP calls)

- Reuses owner-operated Home Assistant MCP v2 on Mac at loopback `http://127.0.0.1:3848/mcp`. New **stdio-only**, narrow proxy `src/lib/teslamon-ha-lights-mcp.mjs` advertises just three tools: `search_lights`, `get_light_state`, `set_light`.
- The proxy always pins search domain to `light`; validates light entity IDs, room names, and allowed light actions `turn_on`, `turn_off`, brightness percentage, color and color temperature. It has **no** generic service passthrough, switch/fan/cover/lock/alarm/garage/automation/script access. Existing HA MCP safety policy is an additional independent boundary.
- TeslaMon's isolated Codex CLI `--ignore-user-config`, read-only sandbox, no interactive approval, and a per-server `default_tools_approval_mode="approve"` preauthorizes **only that three-tool local MCP proxy**, not the full Home Assistant provider or Mac Control/desktop plugins. Model calls are surfaced as `mcp_tool_call` events; server rejects any other MCP/tool execution, >5 MCP calls/turn, >1 light mutation/turn, unsuccessful calls, or a forged `ha_done` plan without a completed actual light tool call. The model directly chooses Home Assistant tools; the old playback output schema still routes video playback to the same current YT Streamer browser tab.
- The signed Cloudflare Access user identity and random per-tab Codex context remain. The browser never sees HA token, PowerALX token, unrestricted HA MCP endpoint, or MCP executable parameters.
- Read-only actual Codex CLI MCP tests: Kitchen and Play Room status lookups completed successfully, then a video `pause` follow-up returned expected playback action in the same Codex thread. Tool catalog contains only three light tools. No physical lights were switched in testing.
